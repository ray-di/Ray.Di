# Threat model

## What this project does and where untrusted input enters

Ray.Di is a PHP dependency injection container, not a service. It reads a module (bindings and interceptor
pointcuts) plus reflection over the classes it injects, and instantiates them. It then keeps two caches, both of
them PHP that is written and read back:

- AOP proxies, generated by Ray.Aop into the `classDir` given to `Injector` (a temp directory by default);
- the serialized `Injector` itself, a documented optimization —
  `unserialize(file_get_contents('*.cache.php'))`, see `demo/10-cache.php`. `Injector::__wakeup()` installs an
  autoloader that `include`s any `<classDir>/<Class_Name>.php` it is asked for.

Untrusted input is therefore a name or a definition that reaches `Container::getInstance()` /
`Dependency::inject()`: an application that maps a route or a configuration value to an interface name gets
there, which makes the container a path from data to `new`. The other entries are the `classDir` (a shared or
predictable path makes the caches writable by someone else) and anything that is `unserialize()`d, including a
cache file an application writes for itself.

## Components that matter most / least

- `src/di/Injector.php`, `src/di/Container.php`, `src/di/Dependency.php`, `src/di/DependencyFactory.php` — the
  path from a name to an instance: reflection, `class_exists()`, autoloading, and the container serialization
  described above.
- `src/di/Argument.php`, `src/di/InjectionPoint.php`, `src/di/InjectionPoints.php` — the `__serialize` /
  `__unserialize` round-trip of the graph. A serialized `Injector` carries these, so their round-trip is a
  boundary even when the container itself is trusted.
- `src/di/Bind.php`, `src/di/BindValidator.php`, `src/di/NewInstance.php`, `src/di/Instance.php`,
  `src/di/Untarget.php`, `src/di/Scope.php` — turning a binding into construction. A binding whose target is
  not assignable to the declared type is high. `BindValidator::to()` checks interfaces only, and `toInstance()`
  and `toConstructor()` do not go through it, so the question is whether a non-assignable object can reach an
  injection point that does not re-check the type.
- `src/di/CompileNullObject.php` and `src/di/NullObjectDependency.php` (through `koriym/null-object`) write
  generated classes into the `classDir`, and `src/di/BindingsMarkdown.php` writes a binding log beside them.
  `src/di/Grapher.php` is a second entry point with the same `__wakeup()` autoloader as `Injector`, and
  `src/di/ModuleString.php` is where a binding graph is rendered as text — the text reaches logs and error
  messages, so it is where a secret in a binding would leak.
- `src/di/MultiBinding/`, `src/di/AspectBind.php`, `src/di/ProviderProvider.php`, `src/di/AssistedInject*.php` —
  configuration-driven. In scope, but interesting mainly where a decision turns into instantiating or
  intercepting something other than what was asked for.

`src-deprecated/` (annotations and the old qualifier handling) is legacy and lower priority.

## How to exercise it

Everything is installed; the network is already gone.

- `raydi-test` runs PHPUnit over `tests/` and `tests-php8/` (`vendor/bin/phpunit`).
- `raydi-demo` runs `php demo/run.php`: thirteen examples, including `10-cache.php` (the serialized-`Injector`
  cache), `11-script-injector.php` (`ScriptDir`), `07-assisted-injection.php` and
  `12-dependency-chain-error-message.php`.
- `tests/di/script/aop.php` builds an `Injector` from a module and writes the serialized result next to itself,
  and `tests/di/script/grapher.php` does the same for a `Grapher`. Both fix their class dir to `tests/tmp`, so
  copy one and edit it to drive a case of your own — they are the shortest way to produce a cache file you can
  then point an attacker at.
- The quality tools are linked into `vendor/bin` from the bin namespace: `vendor/bin/psalm`, `vendor/bin/phpstan`,
  `vendor/bin/phpcs`, `vendor/bin/phpmd`, as `composer sa`, `cs` and `phpmd` call them. `vendor/bin/psalm
  --taint-analysis` is available and worth running over the reflection paths.
- Scratch space: `tests/tmp`, `tests/di/tmp`, `tests/compiler/tmp`, `demo/tmp`. Generated proxies are readable
  PHP; `ReflectionClass::getFileName()` returns the path for a case you build yourself.

## How you rate severity

- Anything that gets from a name, a module definition or an unserialized cache file to executing code, or to
  instantiating a class the caller did not intend, is critical.
- A serialization round-trip that restores a graph behaving differently from the original — a binding, an
  injection point or an argument that changed — is high.
- A leak from a cache file or from an error message is medium, and high when it exposes something secret.
- Denial of service is medium.
- A finding that needs the attacker to write a `classDir` the application owns — the same user, a private
  directory — or to control a cache file the application writes for itself, is low: that attacker already runs
  code as, or already controls data trusted by, the application. It is not low when the `classDir` is the
  default `sys_get_temp_dir()` or any directory a lower-privileged principal can write, because the loader
  prefers an existing `<classDir>/<Class_Name>.php` over regenerating it and `include`s it as the application.
  Report it, and state which case it rests on.

## Anything to leave alone

- `unserialize()` of untrusted data is a known and documented hazard of the cache feature. Report it as a
  property of that API, with the scenario that makes the cache file untrusted, rather than as a new bug.
- The untyped `$module` parameter (`AbstractModule|ModuleList|null`) and the annotation-string handling in
  `src-deprecated/` are known legacy. Report a concrete exploit, not the pattern.
- Coding standards, test coverage and static-analysis baselines are out of scope.
